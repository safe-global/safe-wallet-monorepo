Overall a well-scoped PR — good separation of concerns (lazy feature registry, gate via CGW flag, no-op read layer when disabled), thorough test coverage on the new component, and safe defaults (renders nothing on UNAVAILABLE, no polling once settled). A few things worth addressing:

### 🐞 Bugs / correctness

**1. `isLast` propagation is broken when the Safenet row renders**
`apps/web/src/components/transactions/TxSigners/index.tsx:270,281`

The last `Signed (…)` row and the `Created` row still compute `isLast={!showExecutionRow}`, but there is now potentially a Safenet row after them. When `!showExecutionRow` **and** SafenetAuditRow actually renders (attested check observed), two adjacent rows both claim `isLast=true`, dropping the vertical connector between them.

Complicating factor: `SafenetAuditRow` can return `null` at render time (no snapshot yet, or `UNAVAILABLE`), so the parent doesn't know whether a real row will follow. The cleanest fix is to compute a `willRenderSafenetRow` boolean up here (e.g. move the `useSafenetCheck` call to the parent or expose a small "has snapshot" hook), then thread it into the neighbours' `isLast`. This is the same point [tmjssz raised](https://github.com/safe-global/safe-wallet-monorepo/pull/8485/files#r… ) in his review — worth resolving before merge.

**2. Enabled check performs the lazy import even on chains without the flag**
`apps/web/src/components/transactions/TxSigners/index.tsx:159,287`

`useLoadFeature(SafenetChecksFeature)` triggers the dynamic `import()` for every rendered `TxSigners` regardless of `isSafenetEnabled`. On non-Safenet chains that's a wasted network round trip and defeats the "disabled sessions pay no bundle cost" claim in the PR body.

Move the enabled check inside `SafenetAuditRow` itself (or check enabled first and only call `useLoadFeature` conditionally via a wrapper). Same feedback tmjssz flagged.

### 🧹 Code quality

**3. Dead env-var override**
`apps/web/.env.example:30-31`, `apps/web/src/features/safenet-checks/index.ts:11-12`

`NEXT_PUBLIC_SAFENET_CHECKS_FORCE` duplicates the local feature-flag override UI added in #8288. Two override paths for one flag is a maintenance hazard; drop the env var and the `process.env` branch. tmjssz flagged this as well.

**4. Redundant optional chaining after null check**
`apps/web/src/features/safenet-checks/components/SafenetAuditRow.tsx:79-80`

Line 68 already returns if `!snapshot`, so `snapshot?.events.find(...)` on lines 79-80 can be `snapshot.events.find(...)`.

**5. `useChain('')` on the initial render**
`apps/web/src/features/safenet-checks/components/SafenetAuditRow.tsx:65`

`useChain(snapshot?.chainId ?? '')` is invoked before the snapshot check. `useChain('')` returns `undefined` today, but the intent reads more clearly if the empty-string fallback is dropped or the lookup is gated on `snapshot?.chainId`.

### 🔒 Security / behavioral

Nothing new — the reader (`SafenetReader`) already enforces the oracle allowlist against attacker-chosen proposals, FROST verification is server-of-truth for BENIGN, and the "link only on BENIGN" invariant in `SafenetAuditRow` is correctly enforced (verified by the "MALICIOUS renders without a link" tests).
