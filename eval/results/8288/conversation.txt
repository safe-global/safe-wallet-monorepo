A few things worth improving before merge:

#### Potential issues

- **`FeatureFlagEditor.tsx:59` — switch does not clear an override when returned to config value.** `onCheckedChange` always dispatches `setOverride`, so toggling a row off then on again leaves it "overridden — matches current chain" (green rail + check indicator) instead of returning to a clean, non-overridden state. Users who use the switch as their primary control will accumulate silent overrides that only display as `matchesCurrentChain: true`. Consider auto-dispatching `clearOverride(feature)` when the new value equals `configValue` — matches the "revert override" affordance and prevents this drift. [Fix this →](https://claude.ai/code?q=In%20apps%2Fweb%2Fsrc%2Ffeatures%2Ffeature-flags%2Fcomponents%2FFeatureFlagRow.tsx%20around%20line%2059-63%2C%20the%20Switch%20always%20dispatches%20setOverride.%20When%20value%20%3D%3D%3D%20row.configValue%2C%20it%20should%20dispatch%20clearOverride(row.feature)%20instead%2C%20so%20toggling%20back%20to%20config%20fully%20clears%20the%20override%20(same%20effect%20as%20the%20revert%20button).%20Update%20FeatureFlagRow.test.tsx%20to%20cover%20this%20behavior.&repo=safe-global%2Fsafe-wallet-monorepo)

- **`useFeatureFlagEditorData.ts:32-49` — reads raw chain data, not overridden.** The editor's rows show the *raw config-service* value in `configValue` and `chainScope`, but `useHasFeature` (and everything gated by it) shows the *overridden* value. That's the intended split — but it means the "Config service" column is not affected by overrides even though the switch below it is. Worth a quick doc-comment on `useFeatureFlagEditorData` explaining that `data` here is deliberately un-overridden (the whole point of the editor is to show what the config service delivered vs. your local value).

- **`FeatureFlagRow.tsx:65-78` — hidden Check inside Tooltip.** Using `visibility: hidden` on the trigger with `aria-label` set is subtle: `visibility: hidden` removes the element from both hit-testing *and* the a11y tree, so the tooltip and aria-label are effectively dead when `matchesCurrentChain` is false. That is what you want, but a screen reader user will never hear "Matches config service setting for the current chain" even when it *is* matching, because the `aria-label` is on the icon while the accessible content is inside `TooltipContent` (only exposed on focus/hover). Consider either (a) using `sr-only` text alongside the visible check for reliable a11y, or (b) dropping the `aria-label` on the icon since `TooltipContent` already carries the announcement.

- **`featureFlagOverridesSlice` runs in production.** The reducer is registered unconditionally in `store/index.ts:67` and included in `persistedSlices` (`:95`) + `broadcastState`. `applyFeatureOverrides` is a hard prod no-op, so behavior is fine — but the reducer, persisted state, and broadcast channel still ship. Small cost only; worth flagging that a stale `featureFlagOverrides` localStorage entry (e.g., from prior staging use on the same origin) will silently sit there in prod forever with no way to clear it via UI.

- **`bundleExclusion.test.ts:18` — marker string is not distinctive enough.** `"local feature-flag overrides"` is generic enough that a future unrelated copy change could accidentally satisfy or invalidate the test. Consider a longer, editor-only sentinel (e.g., the full `AlertTitle` string `"Development tool."` combined with the class name, or a dedicated hidden `data-*` attribute in the editor JSX) to make the assertion robust.
