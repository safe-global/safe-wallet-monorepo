Nice, focused PR. The `detectListClusters` primitive with union-find over the OR-relation is a clean model for the "front-4 OR back-4" flagging, and the multi-chain dedup is the right call. A few things worth improving before merge:

### 1. Duplicated & inconsistent similarity computation in the trusted-safes modal

`useTrustedSafesModal.ts:113` computes clusters over the **full** `allSafes` list, while `ManageTrustedSafesContent.tsx:102-103` re-runs `useFlaggedSimilarAddresses` over the **filtered** `availableItems`.

Consequences:
- Two full hook chains (`useSimilarityClusters` → `useListSimilarities` → `detectListSimilarities`) run per render.
- `similarAddressesForSelectAll` and `toggleSelection` use the full-list `flaggedAll` (via `isAddressFlagged`) for confirmation gating, but the table's per-row badge (`flaggedAddresses={flaggedAddresses}` in `SafeAccountsTable`) uses the filtered set. Result: a user searching such that only one of a poisoned pair is visible sees **no badge**, yet still hits the "confirm similar address" dialog when they try to select it. Two sources of truth for what "flagged" means is a UX foot-gun.

Fix: expose `flagged` from `useTrustedSafesModal` and consume it in the content, dropping the second `useFlaggedSimilarAddresses` call.

### 2. `useSimilarityClusters` — anchor and impostor clustering assumes config parity

`useSimilarityClusters.ts:35-37` flags an in-list trusted anchor when an impostor imitates it. But the anchor is **not** added to `groupIdByAddress` — the assumption is that when both anchor and impostor are in the list, `detectListClusters` already grouped them because both engines default to 4/4.

This holds today, but it's a silent coupling between `SimilarityConfig` (`prefixLength`/`suffixLength`) and `AnchorSimilarityConfig` (`prefixThreshold`/`suffixThreshold`). If either is ever tuned independently, the anchor↔impostor pair silently loses its visual grouping while remaining flagged. Consider:
- Stamping the anchor with the impostor's `groupId` here to make the invariant explicit, or
- Adding a comment/test locking the "anchor threshold ≥ list bucket length" contract.

### 3. Minor performance nit

`useSimilarityClusters.ts:35-37` loops all `addresses` even when `imitated.size === 0` (the common case when the flag is off or no anchor matches). Cheap guard:

```ts
if (imitated.size > 0) {
  for (const address of addresses) {
    if (imitated.has(normalizeAddress(address))) flagged.add(address.toLowerCase())
  }
}
```

### 4. Test coverage gap on the composite hook

`detectListClusters` is well-tested at the engine level, and `useFlaggedSimilarAddresses` is tested with `useListSimilarities` mocked. But `useSimilarityClusters` — where the interesting composition (union-find + anchor annotations + "flag the imitated original") happens — has no direct test.

Worth adding at minimum:
- In-list anchor + in-list impostor → both flagged, both share the same `groupId`.
- Out-of-list anchor + in-list impostor → impostor flagged, no `groupId`.
- Flag off (`ADDRESS_POISONING_PROTECTION`) → identical to pure intra-list result.

### 5. `useOnboardingSafes` — "trusted anywhere" scope

`useOnboardingSafes.ts:41-43` defines `trustedAddresses` purely from `allAdded` (pinned). Undeployed safes aren't considered trusted-anywhere, so an undeployed safe that shares an address with an owned one on another chain still ends up under "owned". If that matches product intent, ignore; otherwise consider unioning `Object.keys(allUndeployed[chainId] || {})` into the trusted set too.

### 6. Naming nit

`useListSimilarities` reads like it clusters a list, but it actually only runs the anchor detector (returns `Map<address, ListAnnotation>` where `match` is anchor-based). `useAnchorAnnotations` or `useAnchorListMatches` would signal that more clearly, especially now that the "list clustering" name is taken by `useSimilarityClusters` / `detectListClusters`.

---

Nothing here is a blocker — (1) is the most impactful because it changes user-visible behavior on filtered views.
