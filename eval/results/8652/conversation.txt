#### Findings

**1. Truthiness check on `httpStatus` (minor, consistency)**

In `apps/web/src/services/observability/providers/mixpanel/error-tracking.ts:40` and in `apps/web/src/services/exceptions/index.ts:78`, `httpStatus` is guarded with `context.httpStatus && …` — the same truthiness pattern you deliberately avoided for `attempt`. It's benign in practice (HTTP 0 isn't a valid status), but the mixed conventions in the same mapper invite copy-paste mistakes for the next facet added. Consider `context.httpStatus !== undefined` for symmetry with the `attempt` guard and its explicit rationale comment.

**2. Dedupe-key completeness ≠ `ErrorContext` completeness (PR-description overstatement)**

`error-tracking.ts:131` hashes the *emitted* properties (`JSON.stringify(properties)`), where `properties` is built from `mapContext` — a hand-maintained whitelist. So the "a facet added later cannot be forgotten" claim in the PR body only holds if the new `ErrorContext` field is *also* wired into `mapContext`. A short comment on `mapContext` (or a `satisfies Record<keyof ErrorContext, …>` at the type layer) would make the invariant enforceable, not just documented.

**3. Key-order fragility (informational, not a bug today)**

Dedupe correctness depends on `JSON.stringify` iterating properties in insertion order — currently guaranteed because `properties` is built with a fixed literal + a fixed-order `mapContext` return. If someone later refactors `mapContext` to conditionally add keys in different orders (e.g. via `Object.fromEntries(entries.filter(...))`), two logically-identical events could produce different keys and stop collapsing. Worth an inline note near the `JSON.stringify` call, or a deterministic key builder (sorted keys). Not urgent.

**4. `pruneSentErrors` – small O(n) opportunity (perf, negligible)**

`error-tracking.ts:55-66`: on overflow you scan the whole map twice (expired first, then LRU). At `MAX_TRACKED_ERRORS = 500` this is a rounding error and clarity wins; flagging only because the current shape makes it easy to reach for `Map#entries()` slicing later if the ceiling grows.

**5. Test coverage — one gap worth filling**

The retry-window interaction is well covered, but there's no assertion that `Error Occurrences` is *not* included on a stale spread when the same key resurfaces after the window — i.e. that `state.suppressed` is reset to 0 on re-emit. The current test only checks `occurrences === 3`; adding a follow-up `trackPollFailure()` immediately after the re-emit and asserting the next re-emit at `START + 2×DEDUPE_WINDOW_MS` reports `1` (not `4`) would pin that invariant. Cheap, and it locks in the reset.

---

#### Non-issues (verified)

- Deleting during Map iteration in `pruneSentErrors` — well-defined in JS, safe.
- LRU re-insertion (`delete` then `set`) in `claimOccurrences:84-85` is the right pattern for insertion-order-as-LRU.
- Composite-level test correctly pins the "Mixpanel-only dedupe" invariant — good regression fence.
- `attempt` inclusion in the key is essential for the CF-sync 2s retry case and the tests demonstrate it.

Overall LGTM. All notes are polish, none block merge.
