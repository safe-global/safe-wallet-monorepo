Overall this is a high-quality slice: clear precedence rules, defensible invariants, and tests that compose the real decoder with checked-in beta bytes. Comments are focused on things to improve.

### 🟡 Correctness / robustness

1. **`plainAttested` accepted without a matching `PLAIN_PROPOSED`.**
   `packages/utils/src/features/safenet-checks/utils/deriveCheckState.ts:88-93` — the oracle branch above it doesn't require a matching `ORACLE_PROPOSED` either. On a reorg or partial fetch, a lone `*_ATTESTED` event survives while its proposal has dropped, and the state jumps straight to `BENIGN`/`AWAITING_VERIFICATION`/`VERIFICATION_FAILED`. Consider gating each attested branch on the corresponding proposal event, matching the philosophy already documented for `SUBMITTED` ("must require an actual proposal event"). If this is intentional (the derivation trusts the caller's grouping-by-hash), a one-line comment saying so would prevent a future consumer from "hardening" it in the wrong direction.

2. **`AttestationVerificationStatus.UNVERIFIED` collapses into `AWAITING_VERIFICATION`.**
   Same file, lines 76-93: only `VERIFIED` and `INVALID` are matched explicitly; both `UNVERIFIED` and `PENDING` fall through to `AWAITING_VERIFICATION`. That is likely the intent, but the fallthrough is easy to miss — an added case that returns e.g. `TIMED_OUT` in a future edit would silently start reading as "still working". An exhaustive `switch` (with an `assertNever` default) would lock this in.

3. **`DISPUTE_RESOLVED` alone is not a verdict.**
   Line 39-40 and the PR description note that `resolveDispute` emits `OracleResult` alongside `DisputeResolved`, so this is safe in practice. If a future contract path ever emits `DisputeResolved` without a paired `OracleResult`, the derivation reads as `IN_PROGRESS` indefinitely (or `TIMED_OUT` past deadline), never `MALICIOUS`. Worth a `// invariant:` note on `hasNegativeVerdict` so the coupling to the contract is not implicit.

### 🟢 Minor / cleanup

4. **Two near-identical attestation branches.**
   `deriveCheckState.ts:76-93` — the "attested → verified/invalid/awaiting" logic appears twice. Extracting a small `verdictFromAttestation(attestation)` (returning `BENIGN | VERIFICATION_FAILED | AWAITING_VERIFICATION`) removes the repetition and puts the mapping in one place. Arguable — the current form is very readable.

5. **Type inconsistency: `NormalizedCheckEvent[]` vs `ReadonlyArray<NormalizedCheckEvent>`.**
   `packages/utils/src/features/safenet-checks/types/snapshot.ts:27` uses a mutable array; `deriveCheckState.ts:11` uses `ReadonlyArray`. Prefer `ReadonlyArray` on the snapshot too — it is described as recomputed-from-scratch, so nothing should mutate the collected event list once assembled.

6. **`deadlineBlockOf` allocates a `bigint` per event.**
   `deriveCheckState.ts:19-28` — not a real hot path here, but if the reader ends up folding many checks per poll, comparing decimal-string lengths first and only `BigInt`-ifying the tie-breakers would avoid the allocations. Skip if this stays cold.
