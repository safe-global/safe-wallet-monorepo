Overall this is a low-risk change — the diff is narrow, TDD is well-executed, and the four allowlists that need `'1.5.0'` are all covered. A few things worth improving:

#### 1. Duplicated version arrays — same problem, four call sites (nit / maintainability)

The `['1.3.0', '1.4.1', '1.5.0']` array is inlined in four places:

- `apps/web/src/hooks/useHasUntrustedFallbackHandler.ts:29-33` (CompatibilityFallbackHandler)
- `apps/web/src/features/security/data/scanners/fallbackHandler.ts:17` `COMPATIBILITY_HANDLER_VERSIONS` (CompatibilityFallbackHandler)
- `apps/web/src/utils/transaction-guards.ts:160` (MultiSend)
- `apps/web/src/utils/transaction-guards.ts:420` (SignMessageLib)

The first two encode the same rule ("versions with an official CompatibilityFallbackHandler"), so at minimum those should share a constant. This PR exists precisely because someone forgot to update each of these sites when 1.5.0 shipped — extracting them into shared constants (e.g. co-located with `KNOWN_SAFE_VERSIONS` in `scanners/constants.ts`, or a dedicated `known-versions.ts`) would reduce the odds of the same miss when 1.6.0 arrives.

#### 2. Pre-existing gap: `useHasUntrustedFallbackHandler` doesn't recognise `ExtensibleFallbackHandler`

`apps/web/src/hooks/useHasUntrustedFallbackHandler.ts:29` only checks `getCompatibilityFallbackHandlerDeployments`, but the Security Hub scanner (`scanners/fallbackHandler.ts:36`) additionally trusts the `ExtensibleFallbackHandler` (1.5.0+). If a 1.5.0 Safe ends up using the extensible handler, Security Hub will report clear while the Settings banner still flags it as untrusted — same inconsistency this PR is trying to eliminate elsewhere. Out of scope strictly speaking, but the ticket is "recognise 1.5.0 as trusted **across the app**" so it's worth confirming whether that case is intentionally deferred.

#### 3. `isMigrateToL2TxData` test — minor faithfulness point

`apps/web/src/utils/__tests__/transaction-guards.test.ts:387` hardcodes `getSafeL2SingletonDeployment({ version: '1.4.1' })` as the inner `migrateToL2` argument even in the 1.5.0 MultiSend test. `isMigrateToL2TxData` doesn't validate the L2 singleton, so the test correctly passes, but the "1.5.0 MultiSend + 1.5.0 L2 singleton" scenario isn't exercised end-to-end. Cheap to parameterise if you want the test to represent the real deployment.

#### 4. Positive test for `factoryValidationScanner` on chainId `'1'`

Fine because the 1.5.0 `SafeProxyFactory` (`0x14F2982D…`) is deployed on mainnet — but `SafeVersion` typing plus `hasMatchingDeployment` are the only guards. Worth a mental note that adding a future version to `KNOWN_SAFE_VERSIONS` without a corresponding deployment on any given chain would silently produce "unknown → partial", not a hard error.

Nothing above blocks the merge. LGTM once (1) is addressed or explicitly deferred.
