[clovisdasilvaneto 2026-08-18T14:20:39Z] ## ✅ The pre-merge blocker in the PR body is resolved — this is clear to merge

The "Risks / not checked" section says attribution must be completed from the already-ingested `@error.type:EvalError` events **before this filter ships**, because merging stops further ingestion. **That query has now been run.** Datadog access was granted and the 30-day window was queried directly. The full write-up is on [WA-2952](https://linear.app/safe-global/issue/WA-2952/remove-the-third-party-script-triggering-blocked-code-errors); the short version:

**No vendor script is responsible.** The `@error.source:report` CSP-violation events — which do carry attribution, 13 of them in the window — have stacks reading `at <anonymous> @ chrome-extension:1832:32` and similar. Browser extensions, not Beamer / GTM / Calendly / Cloudflare / hsforms / HubSpot.

**Cloudflare Turnstile is ruled out empirically.** It was the strongest a-priori candidate (loads on the first protected request; 77% of the `EvalError`s occur on `/welcome/spaces`, a login page). But its script loads 53× on `/home` and **zero times on `/welcome/spaces`**.

**The six vendor domains appearing in every event are a false signal** — the browser echoes the entire `script-src` directive inside the error message, so all six match a naive grep on every single event. Worth knowing before anyone re-derives it as evidence.

### This validates the design choice made in review round 2

The `isNotFirstPartyStack` gate treats a **missing stack** as not-first-party and drops it. That default was picked on reasoning; the data now supports it. The `EvalError` cluster arrives with **no stack at all**, which is precisely why the pre-existing extension filter never caught it:

```ts
const originatesFromExtension = (stack) => {
  if (!stack) return false   // stackless events fall straight through
  ...
}
```

So these are almost certainly the same extension-origin noise `filterRumEvent` already intends to drop — it just could not see them.

### One correction to a review note

An earlier review observation held that after this change there would be "no client-side telemetry for CSP violations at all", since no `report-to` endpoint is configured. That is not accurate: `@error.source:report` CSP violations **do** reach Datadog and are the reason this attribution was possible. They are discarded client-side by `NON_USER_IMPACTING_SOURCES`, not missing from ingestion. The follow-up is better framed as "stop dropping the one signal that carries attribution" than "add a reporting endpoint".

### Remaining honesty caveat

The 13 attributed reports and the 69 `EvalError`s are different populations with different page distributions, so "extensions cause the 69" is a strong inference rather than a proof. What is established: extensions demonstrably cause `eval` CSP violations on this app, no vendor is implicated by any evidence, and Turnstile is excluded. Merging no longer forecloses anything — the attribution question has been taken as far as the available data allows.
