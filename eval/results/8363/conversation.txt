### Summary

Clean, focused fix. Detection was already using the combined pool; the bug was only in the post-filter that restricted flags to owned rows. Removing that filter + moving the banner up to the section header level + passing `flaggedAddresses` to both tables is the right shape. Tests cover the WA-2912 regression scenario (both look-alikes pinned).

### Findings

Nothing blocking. A few minor notes:

1. **`SimilarityConfirmDialog` copy** — `index.tsx:207` passes `pendingConfirmation.displayName` into the confirm dialog. Worth double-checking the dialog's copy still reads correctly when the flagged row is in **My accounts** rather than the wallet-owned list — the previous mental model was "you're about to add a look-alike," but with pinned rows we're really saying "one of the safes you already trust looks like another one." If the dialog's body text implies "adding a new safe," it may want a light copy tweak (not necessarily in this PR).

2. **Banner placement when only trusted rows are flagged** — the banner now sits above `My accounts`, which is correct. Just flagging that in the previous UX the banner was inside the *Owned* group; if any spec/UX reference doc mentioned it as an "owned-section warning," that reference is now stale.

3. **`OnboardingSafesList.tsx:11` doc comment** — nit: "trusted and owned rows alike" reads slightly awkwardly. Consider `Lowercased addresses flagged as look-alikes; applies to both trusted and owned rows.` Purely cosmetic.

4. **Test file: `OnboardingSafesList.test.tsx`** — the new banner position assertion uses `compareDocumentPosition`, which is fine but a bit indirect. `expect(banner.compareDocumentPosition(trustedTable) & Node.DOCUMENT_POSITION_FOLLOWING).toBeTruthy()` would be safer if `compareDocumentPosition` ever returned a combined mask. Current strict equality happens to work here because there's no ancestor/descendant relationship between the two nodes.

5. **`useOnboardingSafes.ts:33-37`** — `combinedAddresses` is now a plain merge of `trustedSafeItems.map(...)` + `ownedSafeItems.map(...)`. Since both inputs already come from `allSafes`, you could shortcut to `(allSafes ?? []).map((s) => s.address)` and drop the concat + the two-array dependency. Micro-optimization, purely optional.

- ✅ Regression test for both-pinned look-alikes (`useOnboardingSafes.test.ts`, "WA-2912 regression")
- ✅ Banner rendered when only trusted is flagged
- ✅ Both tables receive the flag set
- ✅ Confirm gate applies to any flagged row via `useOnboardingSelection` test

### Security / perf

No concerns. The detection pool didn't grow — the same combined list was already being scanned. Only downstream visibility of the result changed.
